## 0. 一句话结论

**结果差不是某一个 bug 造成的，而是三层问题叠在一起：**

1. **方法层（最根本）**：EAB（对证据 token 加注意力偏置）在"证据已经全部放进上下文、Qwen3-VL-8B 首 token 几乎确定"的设定下，**原理上推不动答案**。实现没有坏，bias 确实生效了，但它改变答案的幅度跟换一次硬件的数值噪声一样大。这条路走下去，到不了 5%。
2. **协议与评分层**：主指标、基线、校准、检索设置的选择，要么把分数压得很低（WebQA 官方 QA 只有 23），要么让比较不公平（基线是历史缓存、static 基线被格式问题拖垮），要么让方法的组件根本没被测到（512 题全部触发检索，门控形同虚设）。
3. **实验流程层**：同一批开发题被反复调参，"独立确认"批次与前几轮用题重叠，评分器和阈值在看到结果后多次修改。之前报过的几个正结果（+8.43%、+14.4%、+33%）**全部经不起推敲**。

**原作者的东西不用再追**：原作者仓库里根本没有 EAB 实现，论文数字口径不明，"复现不出原论文"不是我们的问题，也不应该再当目标。

## 1. 根因清单（按严重性排序）

### R1【方法·致命】EAB 软偏置在当前设定下没有足够的作用空间【已证实】
- **现象**：512 题同协议五臂（CUDA）中，EAB-P 相对 static 官方 QA +1.30%，95% CI [−0.11, +0.87] 分，跨 0；MPS 上 +1.20%，同样跨 0。✔ `cuda_controls512/.../OFFICIAL_RESULT.json`、`mps_controls512/backend_comparison/REPORT.md`
- **机制**：
  - bias 只在证据块内部重新分配注意力，不改变证据的总注意力质量。
  - Qwen3-VL-8B 首个答案 token 的分布几乎是确定的（预测熵约 0.01–0.02），bias 最大约 1.2 nat（每题最大 bias 中位数 0.78，p90 1.07），不足以翻转首 token。512 题里首 token 只变了 14 题。
  - 64 题机制观测中，支持块的注意力质量确实被推了过去（L1 距离 0.77→0.26），但答案只翻转了 2/64。**注意力在动，答案不动，这条因果链是断的。**
- **噪声对照**：同一模型不加任何 bias，只是从 CUDA 换到 MPS，就有 62/512 题答案不同；EAB-P 改变的答案数（55–64）就是这个量级。✔
- **增益几乎全部来自两道题** ✔：+0.304 分中，`d5df71a0…`（static 答 Jump，EAB 答 Flying，参考答案就是 Flying）贡献 +0.195；`d5dbe88c…`（around→Around，答对率不变，只因大小写更贴近参考句，BART 涨 62 分）贡献 +0.122。**其余 510 题合计 −0.013。** 逐题中位数为 0。按答对率算是 8 题升、11 题降。
- **决定性数字：首 token 间隔大于 bias 造成的位移** ✔：在真实 8B 模型的 64 题探针中，门控开启的 38 题里，首 token top1−top2 的 logit 间隔中位数约 3.4–3.5，bias 引起的最大 logit 位移中位数约 2.0。**29/38 题的间隔大于位移**，最终只翻转了 2 题，而这 2 题的间隔本来就是 0 和 0.75。另外，65% 的题预测熵 h_sem < 0.01。加偏置之前，模型已经把约 59% 的注意力放在支持证据上；加了之后，支持证据的绝对注意力质量平均只多 0.011。
- **上界**（5% 相对提升对应 +1.17 分）：
  - EAB-P 只保留有益改写、丢掉全部有害改写：+0.497 分（+2.1%）✔
  - 关掉门控、每题都加 bias（no_bias_gate），同样只保留有益改写：+0.858 分（+3.7%）
  - 五个臂事后逐题挑最好：+5.05%；32 题开发集七个变体逐题挑最好：+0.26%
  - 对照：指标本身是有余量的。如果每题答对率升到 1、BART 保持 static 的值，QA 还能涨 +4.01 分。EAB 拿到的净答对率增量只占这块余量的约 6%。**余量在答错的题上，而 EAB 很少改答错的题**（55 次改写中 36 次答对率完全没变，只是换了说法）。
- **结论**：这是机制上限，不是实现 bug。加大幅度（去掉 U 缩放）、关掉门控，都能让改写数变多，但净值始终停在 +0.3～+0.45。继续调 γ、起始行、层/头，都不可能稳定拿到 ≥5%。

### R1b【方法·严重】实际偏置远小于公式上界，而且方向不指向正确答案【已证实 ✔】
- **偏置太平**：r_j 是 top-k 检索分的 ECDF，进入 prompt 的文档检索分都挤在高端。门控开启的 306 题中，最好 chunk 相对最差 chunk 的注意力 odds（e^{Δb}）中位数只有 **1.185**，而论文命题在 U=1、r 差满 1 时的上界是 e^{1.2}=3.32。例如 qid `d5d146b6…` 的五份文档 bias 为 0.705 / 0.703 / 0.508 / 0.459 / 0.284，最相关的两份之间的 odds 只有约 1.003。
- **方向不对**：ΔQA 与 bias 极差的 Pearson 相关约 −0.05，与 U 约 +0.08。检索 ECDF 区分的是“哪份文档检索分更高”，而不是“哪份文档含有答案”。
- **粒度太粗**：同一 span 内部的比例不变（`main.tex:240-243`）。答案句和干扰句被一起放大；图像 span 把标题、视觉 token、caption 合成一段，共用同一个 b_j，图像里真正有用的 patch 不会被单独加重。门控开启的图像题上，答对率增量反而是 −0.21。
- **含义**：如果还要做注意力干预，偏置必须作用在“支持事实 vs 干扰事实”上，而不是作用在“检索分都很高的 top-k 彼此之间”。前提是先离线证明 r_j 与“该 chunk 是否含答案”相关，而这份相关性目前不存在。

### R2【实现·已排除】EAB 实现本身没有让 bias 失效的 bug【已证实】
需要明确排除，避免继续往这个方向投入：
- 在 sdpa 路径上，加性 mask 确实生效（CPU 小模型验证过；CUDA 和 MPS 上都有答案改变）。门控关闭的 206 题与 static 逐字相同，解码阶段也加上了 bias。复现代码与 CUDA 快照的 `qwen_eab.py` 逐字相同。
- 早先"从第二个 token 起与 static 完全相同（0/0/32）"，原因是那组用的是 `ans2`（只在解码阶段施加）变体，而且 32 题里只有 17 题开了门控，不是 bug。同一 512 题中 decode-only 改变了 41 个答案。
- **但有一处标签错误，必须修正**：论文公式（`main.tex:228,234`，行 `a ≥ t_end`）对应 `ans1`，而 `erc/run.py:106` 默认跑的是 `ans2`，`erc/tables.py:12` 又把 `ans2` 标成了"EAB 论文式"。✔ 凡是以 `ans2` 为"论文式"报出的数字都要重新标注。
- 次要问题：复现版 `predictive_entropy` 除以 `log(numel)` 而不是 `log(vocab)`（omniaware 已修正）；BRIEF 里"MPS 用 eager"的说法不对，Qwen 推理全部硬编码 sdpa，eager 只用在 BART 评分器上。

### R3【协议·严重】static 基线被答案格式拖垮，所以"相对 static 的提升"没有意义【已证实 ✔】
- **OK-VQA（A100，256 题开发集，官方 VQA accuracy）**：

  | 臂 | direct（不检索） | static（检索 top-5） | gated:static | EAB |
  |---|---:|---:|---:|---:|
  | 分数 | **61.5** | 36.3 | 48.1 | 36.3 |

  配对比较中，direct 胜 static 82 题、输 10 题。
- **主审逐题核查**：检索之后模型答得更长、更具体，在 VQA 精确匹配下被判错。例如：`kentucky derby`（标准答案 kentucky）、`in a bakery`（标准答案 bakery）、`new york city`、`pickup truck`。另一部分是被检索到的段落带偏（rock→bamboo，texas→mexico）。证据里有没有答案都会掉分：含答案的题 direct 43 胜 6 负，不含答案的题 39 胜 4 负。
- **影响**：static 比 direct 低 25 分，是个被破坏的基线。门控"相对 static +12 分"其实是在绕开一个坏掉的基线，而门控本身仍比 direct 低约 13 分。
- **门控的真实上限**：完美门控 max(direct, static)=64.4，只比 direct 高 2.9 分（约 +4.7%）。也就是说，**在当前检索语料和格式下，就算门控完美，相对强基线也到不了 5%**，必须先把"检索后作答"这条路修好。
- 汇总表里的"+33%（WebQA）/+15%（OK-VQA）"，比的是历史缓存基线（提示、预算、检索打分都不同）。缓存 static 17.9 与同批 512 题 static 23.4 就差了 5.5 分。**这些数字不能进论文主表。**

### R4【指标·严重】WebQA 官方 QA 分被 BART 项主导，与"答对没有"严重脱钩【已证实 ✔】
- 512 题 static：acc_approx 59.1，归一化 BART 27.4，QA = acc × BART = 23.4。图像题 acc 63.2，QA 却只有 13.8；文本题 acc 55.0，QA 33.0（两个子集的排序反了过来）。
- 203 道 acc=1 的题中，110 道的 BART 因子低于 0.5。如果答对的题 BART 因子都为 1，QA 能增加约 35.7 分，**比五个臂之间 0.3 分的差距大两个数量级**。
- 参考答案是完整句子（如 "They are each 225 feet long."），模型给的是短语或带括号的数值（"225 ft (69 m)"），事实对了也几乎拿不到分。BART 还对大小写敏感（Sorrel 与 sorrel 得分不同）。
- **含义**：WebQA 上任何方法的 QA 差异，都很容易被"回答写成什么样"淹没。用 QA 作唯一主指标，方法信号会被格式噪声盖住。

### R5【协议·严重】方法组件没有被真正测到【已证实】
- **门控从未关闭**：512 题全部触发检索（τ=0.15，u_pre 最小值 0.357、中位数 0.60），MPS 上同样是 512/512。WebQA 上的"完整系统"实际等于"始终检索 + EAB"。✔
- **U_omni 基本没有区分力**：u_pre 对答错的 AUROC 约 0.52，文本子集 0.445（方向反了）。U 与 h_grd 的相关系数是 0.93，h_grd 又饱和在 0.80–0.96。U 实际上是一个近乎常数的启发量。
- **r_j 质量中等**：最高 r 块是支持块的比例为 43/61（70%），AUC 约 0.76；但 18/64 题最高 r 的是负例，bias 会把注意力推向错误证据。
- **校准集太小**：WebQA 只用了 64 题（有时 32 题），U 的中位数/IQR、ECDF 和 τ 都从这里估计。
- **WebQA 用的是 distractor 设置**：每题自带约 32 条候选（约 1.4 条 gold），gold-in-top5 为 90/96 和 87/96。检索几乎不会失败，所以门控"要不要检索"的决策天然没有作用空间。论文声称用的是约 39 万条的全局池。

### R6【流程·严重】正结果都来自小样本、已消费的开发题或协议变化【已证实】
- 训练式控制器的"round3_set3 +8.43%"：58 个改动答案中 19 升 20 降；按答对率算平均 −0.95 分；QA 增量的 97% 来自 43 个答对率不变、只改措辞的答案；CI [−0.94%, +22.36%]。其余确认轮的 CI 全部跨 0，文本子集多为负。
- x4 scale 在 32 题开发集上选出来，报告 +14.4%；合并独立批次后变成 −5% 到 −6%。"独立"确认批次大多与前几轮用题重叠。
- 阈值 τ 从 0.35 改为 0.15 后才出现"62→67"；choose 规则修改让 EAB 从 +4.0% 变成 +6.5%；OK-VQA 的 τ 从开发阶段的 0.35 改为确认阶段的 0.95；评分器被多次替换（MMQA 80.4→86.3 经历了多轮修改）。
- 4966 题全量（seed17）：带门控的 EAB 相对一直用 static 为 −2.3%。seed23/29 的官方分没算完。
- 台账 180 行中约 1/3 日期未知，约 126 行没有预注册证明。

### R7【评分·中等】评分口径不统一【已证实】
- 复现用的宽松评分（`erc/scoring.py`）与官方 acc_approx 在 2560 条上均值差 10.5 分（0.699 对 0.594）。按 0.5 二值化后有 761 条不一致，YesNo 题里像 "No, … are not taller" 这类正确否定也被官方判为 0。不同分析者给出的不一致条数不同（430 或 761），取决于定义，但方向一致。
- OK-VQA 的官方 VQA soft accuracy 函数写好了却没被调用（`erc/scoring.py:128-131`），主流程用的是"10 个标注答案里任一子串命中"的宽松判法。同一批 static，宽松分 65.8，官方分约 47.9。

### R8【论文·审稿风险】论文声明与实现或数据不符【已证实】
- EAB 作用的行集合，公式（`a ≥ t_end`）与正文（`a ≥ t_ans`）不一致；代码默认又是第三种（`ans2`）。
- EAB 门控实际用的是 U_post，而不是论文所说的检索时的 U。
- cuda512 的检索规则 `original_retrieve or p_image<0.5` 用了训练过的 query 分类器，与论文"不训练 router"的说法冲突。
- 论文说校准集"来自 validation、与 test 不相交"，但 WebQA 报告的是全部 4966 道 val。
- Table 20 的"选定点"恰好是测试集网格上的最大值，并且就是 Table 1 的报告值。
- ±0.2 的标准差小于 5046 题二项分布的标准误（约 0.66 分）。贪心解码下的"3 seeds"不构成统计误差。
- 之前那份针对 omniaware 仓库的静态审查（`REVIEW_2026-10-10.md`）里，F-1（VideoRAG-Synth 评测集为空）、F-2（M2-RAG 在 OK-VQA 上看不到问题图片）、S-4（对照组都沿用了 Omni-Aware 自己的路由）、S-5（SeaKR 只跑了 1000 题）等问题同样会进入论文表格，需要一起修。

## 2. 原作者材料：一段话带过

证据包里的"原作者代码"（`self-aware-mrag-main`，338 个 .py）是更早的 Self-Aware-MRAG 项目，**不含任何 EAB 或 attention bias 实现**（`_get_visual_attention` 注明"当前未使用"），也不含 WebQA 和论文 Table 1 的数字 ✔。它的 ablation 结果是硬编码的模拟值（`run_ablation_simple.py:131-199`），宽松判分能把同一批 100 题预测从 59 抬到 72。WebQA 在 `dataset_registry.py` 中是 `enabled=False`；Qwen 流程用的是“小写后包含”或“金标里任意长度大于 2 的词出现在答案里”的判分（`self_aware_pipeline_qwen3vl.py` 约 1176–1200 行），生成长度只有 `max_new_tokens=5`，而且生成时根本不改 attention，只改文档的选择和顺序。原论文数字（WebQA 72.85、OK-VQA 67.88）与我们的宽松尺度接近，与官方尺度不一致，口径无法核对。**结论：不再把原论文数字当复现目标，也不用原作者材料证明任何事。**

## 3. 怎么改：从"注意力软偏置"转向能真正改变答案的控制

核心思路：数据显示，**真正决定对错的是"检索到什么、放不放进去、答案写成什么样"**，而不是"已放进去的证据被多看一点"。方法的贡献点应当挪到这里。

### 3.1 先修协议（不改方法，几天内可完成，且是任何结论的前提）
| # | 改动 | 依据 | 最小验证 |
|---|---|---|---|
| P1 | **修好 static**：规范答案格式（OK-VQA 输出短答案并做 VQA 标准化；WebQA 按参考答案的句式输出完整句子），加上 reranker | R3、R4：格式损失占主导 | OK-VQA 256 开发题重跑 direct / static / rerank-static，目标是 static ≥ direct |
| P2 | **强基线定义**：每个数据集取校准集上最强的无门控基线（direct、static、rerank-static 中的最大者）作分母 | R3 | 主表改用强基线作分母 |
| P3 | **指标**：OK-VQA 用官方 VQA accuracy；WebQA 以 acc_approx 为主，QA_approx 和 BART 作补充，并分图像/文本报告 | R4、R7 | 用已有预测重算即可，不需要新推理 |
| P4 | **切分**：校准集 ≥500 题，取自 train；开发集 256 题；测试集只跑一次；三者两两不交并在代码里断言 | R5、R6、R8 | 写入 dev_decisions，test 阶段校验 sha256 |
| P5 | **WebQA 改用开放检索**（`webqa_open_*` 全局池）作主结果，distractor 结果放附录 | R5：distractor 下检索几乎完美，门控没有作用空间 | open_img 256 开发题：gold-in-top-k，以及 direct / static / 门控 |
| P6 | **所有臂在同一次运行中同时解码**，废弃历史缓存基线 | R3、R6 | 一次完整运行 |
| P7 | **预注册**：沿用 omniaware 的 DEV_DECISIONS 机制，多重比较用 max-statistic bootstrap | R6 | — |

### 3.2 方法改造（按"有数据支持"的程度排序）
| # | 方向 | 依据 | 最小验证（只在开发集上做） |
|---|---|---|---|

| M2 | **效用门控**：只在"检索预期比直答更好"时检索。用校准集上的 P(对\|检索) − P(对\|直答) 训练或拟合阈值，而不是"准确率最大的 τ" | R3：direct 比 static 好得多，但仍有 10–15% 的题检索更好（oracle 64.4 对 61.5） | OK-VQA 开发集：门控能拿到 oracle 差距（2.9 分）的多大比例 |
