## 0. 一句话结论

方法核心（EAB 注意力钩子、U 的计算、M·H 路由）实现得比较扎实：A 组用独立的无缓存参考实现做了逐 logit 比对，首 token logits 最大差 1.5e-7。**问题集中在"实验协议与对照"这一层**：

- 一个数据集的评测集在默认参数下是空的；
- 论文声称的评测规模、"所有设置都在 dev 上定好"、"γ/β/τ_b 在 dev 上选" 都与代码不符；
- M2-RAG 在 OK-VQA 上看不到问题图片；SeaKR 只跑了 1000 题；冷启动数据集上所有对照都继承了 Omni-Aware 自己的路由；
- 多处静默回退和只按 qid 命中的缓存，会让错误结果"安静地"进入论文表格。

旧仓库的问题里，"带标签选阈值""宽松子串匹配评分""baseline 复用旧预测缓存"基本修掉了；但**"在测试集上调参"和"论文数字/声明无来源"仍以新形式存在**，"校准集与评测集重叠"在消融实验中以"dev 题混进 test"的形式重现（S3）。

## 2. 严重问题（会让某个结论不可信、对照不公平，或让论文声明不成立）

### S-1 论文声称的评测规模与代码实际划分不符，"no number comes from development questions" 与"evaluate all 4,966"互相矛盾【已证实·主审复核】
- **位置**：`paper/sec_experiments.tex:8,18`；`src/omniaware/data.py:370-371`；`run.py:244-245`。
- **证据**：WebQA 的 calib 取自 train（`calib_pool`），于是 `rest = 全部 4966`，再从中切出 dev 256，test 就只剩 **4,710**。按同样的逻辑：WebQA-img 为 2,511 − 256 = **2,255**；OK-VQA heldout 为 5,046 − 500 − 256 = **4,290**；HybridQA 为 2,000 − 756 = **1,244**。论文却写 "We evaluate all 4,966 validation questions… (2,000 HybridQA and 374 VideoRAG-Synth questions)"。两次划分互相独立：用论文的 2,511/2,455 规模、种子 2027 调用 `split_examples`，full 的 dev 里有 133 道图像题，其中 **118** 道落在 webimg 的 test 里。`dev_select` 用 full 的 dev 分数选全局 EAB 形式，这些题随后出现在 WebQA-img 的报告列。真实 guid 会改变具体题号，期望数量约 116。
- **影响**：要么论文的规模说法是错的，要么如果按论文去跑全量，dev 题就会混进评测，与"no number in this paper comes from development questions"冲突。WebQA-img 主列目前已经直接违反这句话。WebQA-img 列还含有参加过选型的题，而且它不是 4,710 里的图像子集。
- **修复**：只划分一次全量 val，webimg 定义为这次 test 中的图像题。论文改写为实际 N；若坚持评测全部 4,966，dev 必须改从 train 切出，并且不再用 val 做选型。

### S-2 "γ、β、τ_b 在 dev 上选定" 没有代码支撑；β×τ_b 网格实际跑在 test 上，并被拿来论证 "β=0.30 最优"；多处写死的数字无来源【已证实·主审复核】
- **位置**：`paper/sec_appendix.tex:9`（"γ is chosen from {0.6,0.9,1.2,1.5,2.0} on development queries, and applying EAB to all decoder layers outperforms … the last four by 0.6 points"），`sec_appendix.tex:66`（"β and τ_b were selected on development queries… \ai{β=0.30 scores highest at every τ_b on OK-VQA}"），`sec_appendix.tex:69-71`（τ 扫描），`paper/main.tex:130`（"…by \ph\% to 70\%"），`scripts/paper_runs.py:84-90,147-150,250`，`src/omniaware/pipeline.py:166-171`。
- **证据**：
  - dev 阶段（`paper_runs.py:81-91`）只比较 6 种 EAB 形式、3 种 U 变体、3 种 OK-VQA 语料，**没有 γ 网格**，也没有 β、τ_b、τ 的扫描。
  - β×τ_b 网格（`paper_runs.py:147-150`）用的是 `--split` 的默认值 `test`（`paper_runs.py:250`）。
  - `Variant.layers` 只有 `all/mid/late` 三个选项，**根本没有"最后四层"**，所以 "0.6 points" 不可能由本仓库产出。
  - 没有任何命令传入 `--tau`，τ 扫描无法产出。
  - "70%" 是写死的数字，没有对应命令。
  - (τ, τ_b, β, γ, δ) = (0.35, 0.40, 0.30, 1.2, 0.08) 在仓库中找不到任何选择记录（`run.py:147-149`、`routing.py:15`、`DEV_DECISIONS.md:23`）。
- **影响**：这正是旧仓库"在测试集上调参""数字无来源"问题的延续。如果这组超参数最初来自旧仓库在测试集上的调参（【推测】，需要旧仓库的实验日志或提交历史才能确认），那么整个测试集都已被污染。附录 "β=0.30 scores highest at every τ_b" 是在评测集上做的选择性陈述。
- **修复**：（1）在 dev 阶段加入 γ ∈ {0.6,…,2.0}、β、τ_b 的网格，由 `dev_select` 冻结，β×τ_b 敏感性改为只报告不选择；（2）删除"最后四层 0.6 点"，或补充 `layers=last4` 变体并在 dev 上跑；（3）为 τ 扫描补命令；（4）在 `DEV_DECISIONS.md` 中写明这五个超参数的来历，若来自旧仓库则如实披露。

### S-3 校准规模消融（n_calib=100/1000）改变了 test 集本身：n=100 时 test 包含全部 256 道主 dev 题【已证实·主审复核】
- **位置**：`data.py:370-371`；`paper_runs.py:144-146`。
- **证据**：heldout 模式下 `dev = order[n_calib:n_calib+256]`，`test = order[n_calib+256:]`。n_calib=100 时 test 从 order[356] 开始，包含了主实验的 dev 区间 order[500:756]；n_calib=1000 时 test 从 order[1256] 开始，丢掉了 500 道主 test 题。复现脚本为 `exp1_split_vs_ncalib.py`、`split_check.py`。
- **影响**：OK-VQA 上的 "calibration size" 消融，在不同的评测题集合上比较不同的 n_calib，差异混入了题集变化；n=100 时还违反了"dev 不进入评测"。
- **修复**：先用固定种子切出 dev 和 test，再从专门的 calib 池里取前 n 个做校准，保证 test 与 n_calib 无关；或者固定 calib 池大小上限为 1000，消融时只取前缀。

### S-4 冷启动数据集上，Static / CE / FiTM / M2-RAG / SeaKR 都继承了 Omni-Aware 的探测轮和 M_m·H_m 路由【已证实·主审复核】
- **位置**：`scripts/paper_runs.py:59-63`（COLD 数据集一律加 `--probe-uncertainty --first-round-routing`），`run.py:553,564-566`（`chunks = select_chunks(…, route)`），`run.py:52-56`（按路由过滤候选），`run.py:632-660`（FiTM、M2-RAG、SeaKR 都用这个 `chunks`）。
- **证据**：WebQA、HybridQA、VideoRAG 上的 "static" 臂读的是"探测 prefill → M·H 选出模态 → 在该模态内取 top-k"，而不是论文所说的 "always-retrieve static concatenation"。OK-VQA 没有这一步（`COLD` 不含 okvqa），所以各数据集上的基线定义不一致。
- **影响**：（1）主表中 "Static concatenation" 及其它对照实际都用上了本文的路由，路由的贡献在主表中看不到，而对照也拿到了本文的一部分方法；（2）"Of its gain over always-retrieve static concatenation, the retrieval decision accounts for … and EAB for …"（sec_experiments.tex:52）的分解并不包含路由；（3）Static 臂的延迟没有计入探测 prefill（见 M-9）。论文虽然写了 "same packed input"，但没有披露这一点。（4）探测轮本身是全局 top-5（`run.py:388`，`route=None`），`paper_runs` 不传 `--min-per-modality`。WebQA 开放检索每题有文本 top-5 和图像 top-5；若校准相关度把前 5 名都给了文本，图像根本不会进入探测 prefill，`evidence_route` 只能在已经留下的模态里选择，丢掉的模态不会被补回来。路由表里的一部分错误路由是“相关度先填满了探测集”，不是 \(M_m H_m\) 的决定。
- **修复**：增加真正的 joint top-k static 臂（不探测、不路由），主表报告它；当前这个臂改名为 "static (shared route)"，或者在论文中明确披露。

### S-5 SeaKR 行只在前 1,000 道测试题上运行，与同表其它行的题集不同，论文未披露【已证实·主审复核】

### S-6 UniversalRAG 行有两个单元格没有任何命令产出；路由器是手工步骤；路由到语料中不存在的模态时会静默退化为全模态检索【已证实·主审复核】
- **位置**：`scripts/paper_runs.py:125-134`（只跑 `webqa_open_full/hybridqa/videorag_synth`，router 那一步只是 `echo`），`paper/sec_experiments.tex:41`（主表有 WebQA-img 和 OK-VQA 两列），`src/omniaware/baselines/universalrag.py:62-69`，`run.py:52-56`。
- **证据**：`to_route` 返回 `retrieve = bool(mapped)`、`modalities = sorted(mapped & available)`。当路由标签都不在语料中时，结果是 `retrieve=True, modalities=[]`，`select_chunks` 因为 `route["modalities"]` 为空而不过滤，于是退化为联合 top-k（C 组 B6、G 组 F3 复现）。另外，未知标签在 `parse_labels` 中会被静默丢弃并变成 `["no"]`（G 组 F13）。
- **影响**：OK-VQA 的 UniversalRAG 单元格没有来源；WebQA-img 只能从 full 运行中取子集，但这一步也没有命令。"静默退化"让 UniversalRAG 的行为偏离上游（上游会只检索指定模态，或不检索）。
- **补证**：`data.py:234-235` 与 `universalrag.py:25-26` 把 `clip` 和 `video` 都映射成 `"video"`。VideoRAG 的候选是整段视频和片段各 top-5，路由无法只留其中一种；套件 gold 经常只写 `video`，于是“路由正确”仍会把两种块一起送进模型。`routing_metrics.py:17-28` 在 `route.modalities` 为空时，不看实际送进模型的 `chunk_modalities`，改用命令行里的全部模态（默认 image+text）。两道题的块全是文本时，脚本仍输出 coverage 100、Mod/q = 2.0、路线 `image+text`。`tests/test_routing_rules.py:33-39` 把这个空列表记成 “all modalities” 并锁进测试。论文表里 All modalities 的 Cov.=100、Mod/q=2.00 可以由这个替换得到，即使得分列来自全局 top-5。
- **修复**：补 OK-VQA 和 WebQA-img 的命令，或在表中标"—"；把 router 推理写成可执行脚本，并固定 checkpoint；`retrieve` 改为与候选池求交之后非空才为真；`clip` 与 `video` 保持不同标签。

### S-7 `dev_decisions.json` 缺失或模型不匹配时，test 阶段静默使用硬编码默认值；`dev_select` 在没有 dev 结果时也照样写出"决定"【已证实】
- **位置**：`scripts/paper_runs.py:34-40,260`，`scripts/analysis/dev_select.py:46-54,70,110-127`。
- **证据**：`decisions()` 在文件不存在时 `return dict(DEFAULTS)`，`--list` 仍把它显示为 "frozen choices"。`dev_select` 在 dev 为空时 NaN 进入 `max()`，得到任意选择，exit 0（`exp8_dev_select_empty.py`，G 组 F2 复现）。

### S-19 因果表的 Mask 没有挡住注意力，反事实替换会留下原答案【已证实】
- **为何严重**：Table causal 用来论证答案依赖被强调的证据块。入选条件和编辑都对不上这个主张。
- **位置**：`run.py:327-328,499-500`；`interventions.py:38-50,105-125,172-177`。
- **证据**：入选要求检索已触发、某个 EAB 变体活跃，且 gold 字符串出现在检索到的**文本**块里；目标是相关度最高的这样一块，不是偏置最大的那一块。WebQA-img 的 gold 事实按定义包含图像，caption 不算。Mask 只把 token id 改成 pad，pad 缺失时用 EOS（`run.py:499-500`），不改 attention mask，EAB 仍会给这段加偏置。反事实只替换 `answer_span` 选中的一个 gold：`"New York and NYC"`、gold 为 `["New York","NYC"]`、实体 `"Rome"` 得到 `"Rome and NYC"`。随机编辑按 gold 的字符数从词首切一段，再换成可能更长的实体：`"Beautiful city of Paris and NYC."`、gold `"Paris"`、实体 `"Barcelona"`、种子 `"s"` 得到 `"Beautiful Barcelonaof Paris and NYC."`。等长 gold 的选用顺序受 `PYTHONHASHSEED` 影响。`"there is no way"` 对实体 `"no"` 会被 `matches` 记为跟随。
- **影响**：Mask 列不是“证据被移除”。CF 列里原答案别名可以还在块里。随机对照不是等长词替换，而且做不成的题只从对照里丢掉，分母和 CF 不同。这些率不能写成 WebQA-img 上的总体效应。
- **修复**：Mask 用 attention mask 盖住该 span，并停止对它加 EAB。反事实替换全部别名。随机编辑换成等长的完整词，并与 CF 用同一批题。丢掉归一化后变成空串或单字符的 gold。表里报告入选比例，并写明目标块是“含答案的最高相关度文本块”，不是被偏置最多的块。`intervene` 目前只重解码 static 和 EAB 变体（`run.py:323-324`），不重解码 `replication`。因果表若有 Replication 的 Mask/CF/Misled 列，这些格子没有生成路径；Gold@2–5 和噪声列则来自别的、非 cite 的运行。

### S-20 消融表的 AP 列评的不是门控答案；冷启动校准迁移没有换掉门控分布【已证实】

## 6. 总体判断：按 README 在真实服务器上从零跑一遍，最可能卡在哪里

按执行顺序：

1. **§3 下载模型**：只要中断过一次，半成品权重就会被永久跳过（S-11），`check_assets` 也会放行，直到加载 8B 模型时才崩溃。
